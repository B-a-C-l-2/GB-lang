# GB 性能基准（对照 Python）

同一批工作负载分别用 GB 和等价的 Python 实现跑一遍，比较耗时。用途只有一个：
量化「树遍历解释器 vs CPython」的数量级差距，**不是**给 GB 定性能指标。

## 怎么跑

```bash
python benchmarks/compare.py              # 全部用例，每个测 2 轮取最优（约 25 秒）
python benchmarks/compare.py --runs 3     # 测 3 轮
python benchmarks/compare.py --case sort  # 只测一个用例
```

单独运行某一侧（输出校验和，两边应完全一致）：

```bash
python -m gb benchmarks/bench.gb < 用例名
python benchmarks/bench.py < 用例名
```

用例名：`arith` / `calls` / `recur` / `arrays` / `strings` / `structs` / `sort`。

## 测量方法

- **先比校验和，再比时间**：两侧对每个用例都打印校验和，不一致时 `compare.py` 直接以
  非零码退出。校验和不同说明两个实现已经不等价，此时的耗时对比没有意义。
- **消除进程启动开销**。直接量「跑一次脚本的总时长」是错的：Python 进程启动要
  60–80ms，而它的实际计算只有 1–3ms，结果基本在量启动时间。因此：
  - GB 侧：脚本没有时钟内建（也不为此改语言），用外部斜率法——同一用例跑 1 次与
    4 次各量总时长，`(t₄ - t₁) / 3` 即单次计算时间，启动开销被消掉；
  - Python 侧：在进程内直接调用同一批函数，用 `perf_counter` 计时，天然不含启动。
- 每个用例重复测量取最小值，减少调度噪声。

## 结果

单次计算时间（进程启动已扣除），best of 2：

| 用例 | 工作负载 | GB | Python | 倍率 |
|---|---|---:|---:|---:|
| `arith` | 整型算术循环 4 万次 | 249.20 ms | 2.40 ms | **103.9x** |
| `calls` | 函数调用 2 万次 | 220.48 ms | 1.42 ms | **154.9x** |
| `recur` | 递归 `fib(21)` | 184.58 ms | 1.11 ms | **167.0x** |
| `arrays` | 数组 push / 遍历 / pop 2 万 | 242.29 ms | 1.79 ms | **135.7x** |
| `strings` | 字符串拼接 + 切片 6 千 | 62.49 ms | 0.80 ms | **77.8x** |
| `structs` | struct 构造 + 字段读写 2 万 | 213.29 ms | 2.71 ms | **78.7x** |
| `sort` | 冒泡排序 150 元素 | 168.26 ms | 0.70 ms | **241.0x** |
| **合计** | | **1340.58 ms** | **10.93 ms** | **122.7x** |

补充数据：

- 同一套用例的另一次测量（best of 3）为 **1335.26 ms / 10.92 ms / 122.2x**，与上表差
  异 < 3%，可用于判断噪声量级
- GB 进程启动（含 `gb` 包导入）约 **93–101 ms**，跑三五行的小脚本时这部分比计算本身还大
- 折算单次 AST 节点求值约 **360–400 ns**

## 解读

倍率在 78x–241x 之间波动，原因是实现结构，不是语言语义：

- **`sort` 最差（241x）**：冒泡内层每轮比较要约 38 次 AST 求值——`a[j] > a[j + 1]` 里
  每个下标、每次变量访问都是独立节点；Python 侧用原生列表索引一次完成
- **`_exec_body` 每轮循环都新建 `Environment` 并扫一遍语句做声明提升**：`arith` 用例
  4 万轮循环里它被调用 40,007 次，即每轮分配一个作用域对象
- **类型检查开销大**：`arith` 用例中 `_is_num` 被调用 48 万次、`isinstance` 160 万次
  （每个二元运算都要两次类型判定）
- **`structs` / `strings` 最好（约 78x）**：这类负载把更多工作交给 Python 层的原生
  操作（`push` / `pop` / 切片），GB 的调度开销被摊薄

`python -m cProfile -s tottime -m gb benchmarks/bench.gb` 可复现上述热点。

## 结论

**不为这个数字优化。** 理由同 `AGENT.md` 的项目原则：个人 demo，不追求性能；且这是
实现层次的差距（树遍历解释器对 CPython 慢两个数量级属正常水位），不是语义缺陷。
122x 的实际含义是「GB 里 20 万次循环约 1.3 秒」，对 demo 规模无感。

若将来真要优化，按性价比只有三个靶子：循环体环境复用（最便宜）→ 名字解析缓存 →
调用帧简化。它们都要改求值器结构，收益上限约 2–3 倍，追不回两个数量级。

## 数据的边界

单机、单次测量的微基准，只用于判断数量级和相对热点，不用于横比不同机器；改动
`gb/` 下的求值器或更换 Python 版本后，数字会变，需要重跑。
